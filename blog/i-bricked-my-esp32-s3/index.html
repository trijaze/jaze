Preface: The Accidental Lockout


Locking yourself out of your own hardware using your own security features is a familiar hazard in embedded security.


While preparing a hardware challenge for V1T CTF 2026, I enabled hardware Flash Encryption on an ESP32-S3 development board. Once the challenge was packaged and verified, I wanted to reuse the board for an ordinary test sketch.


Instead of booting, the board entered an unrecoverable bootloop. Because flash encryption was active at the silicon level, the CPU treated plaintext code as ciphertext and crashed on invalid instructions.


This post walks through what happened under the hood, how eFuses govern boot security on the ESP32-S3, and how Espressif's parity-based counter mechanism allowed me to recover the chip without desoldering.


1. Challenge Setup: Designing "XTS-02"


For V1T CTF 2026, I authored a hardware challenge centered on the ESP32-S3 hardware Flash Encryption engine (XTS-AES-128).


The challenge architecture involved:


  1. An ESP-IDF firmware built with CONFIG_SECURE_FLASH_ENC_ENABLED=y in Development mode.
  2. A provisioning Python script (tools/provision.py) to write vendor keys into BLOCK_KEY0 and metadata into BLOCK_USR_DATA.
  3. Physical flash dumps for participants to analyze, reverse-engineer key derivation routines, and examine hardware-level encryption boundaries.


To verify the challenge on actual silicon, I used an ESP32-S3 Super Mini (QFN56, Silicon v0.2, 4MB Flash, native USB-C).


I connected the board to COM10, flashed the firmware, ran the provisioning script with --commit, and verified the boot output:



The challenge functioned as designed. The flag was verified, and the challenge was archived for the competition.


2. The Next Day: Bootloops and Silicon State


The next day, I needed the ESP32-S3 board for a different project: a standard Arduino sketch reading sensor data over USB Serial.


I opened VSCode, compiled the unencrypted binary, and uploaded it to the board.


When I opened the serial monitor, the console produced continuous register dumps and watchdog resets:



I ran erase-flash using esptool:



The erase operation completed, but reflashing a clean bootloader and minimal sketch produced the exact same crash loop.


The reason is the distinction between flash memory and eFuses. While SPI flash can be erased repeatedly, eFuses are One-Time Programmable (OTP) physical fuses etched into the silicon. Once burned, a bit cannot be cleared back to zero.


The bootloader had executed the security configuration from the day before:


  1. It burned hardware Flash Encryption into the chip.
  2. It permanently disabled hardware and USB JTAG debugging (DIS_PAD_JTAG = 1, DIS_USB_JTAG = 1).
  3. It write-protected the internal AES key block.


Because Flash Encryption was enabled in hardware, every CPU instruction fetch passed through the internal XTS-AES decryption engine. When plaintext firmware was written to flash, the hardware attempted to decrypt it before execution. The resulting data was invalid machine code, triggering an immediate IllegalInstruction exception on Core 0.


3. Querying the Security State


Before executing further commands, I queried the chip's current eFuse registers using esptool and espefuse:



The output summarized the security configuration:

JTAG was permanently disabled because those fuses cannot be reset.


However, the key register is SPI_BOOT_CRYPT_CNT:



The register is a 3-bit field rather than a single bit.


4. The Mechanism: Bit-Count Parity


In silicon, OTP fuses can only transition from 0 to 1. If Flash Encryption were controlled by a single 1-bit flag (0 = OFF, 1 = ON), testing encryption on a development board would make that board permanently encrypted.


To allow testing during development, Espressif implemented Bit-Count Parity for SPI_BOOT_CRYPT_CNT in Development mode.


The hardware bootloader evaluates the number of set bits (1s) in the register:



State interpretation:


  • 0 bits set (0b000 = 0): Even count -> Flash Encryption DISABLED (Factory state).
  • 1 bit set (0b001 = 1): Odd count -> Flash Encryption ENABLED (Locked in development mode).
  • 2 bits set (0b011 = 3): Even count -> Flash Encryption DISABLED (Recovery state).
  • 3 bits set (0b111 = 7): Odd count -> Flash Encryption ENABLED (Final state, no remaining bits).


Because the board was at 0b001, two unburned bits remained in the register. Since the field was not write-protected, burning one additional bit transitioned the register from 0b001 to 0b011 (decimal 3).


With two bits set, the count is even, and the hardware disables flash decryption during boot.

6. Key Takeaways


  1. eFuse changes are permanent: When testing security features, the bootloader treats commands as definitive. Disabling JTAG (DIS_PAD_JTAG, DIS_USB_JTAG) cannot be reversed by software or flashing routines.
  2. Parity counters provide a deliberate development safeguard: Designing SPI_BOOT_CRYPT_CNT as an odd-even parity register rather than a single boolean flag provides an engineered mechanism to disable encryption during testing.
  3. Counter state on this unit: The register on this board is currently 0b011 (value 3). If encryption is enabled again, the value will become 0b111 (value 7), consuming the final bit and permanently enabling flash encryption on this chip.
