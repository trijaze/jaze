Challenge 1: Green Goblin (OS Internals & Volatility 3 Memory Forensics)


Players are supplied with a single 5 GB memory acquisition: GreenGoblin.raw.


1. Challenge Intel & Architecture


The challenge briefing provides a critical operational clue:


The Green Goblin harnessed a secret Dark Energy to attack our system. Fortunately, our defenses froze his payload mid-execution, shattering his Dark Energy into 5 fragments scattered across the OS internals (R, KO, D, EL and M). Can you recover all 5 fragments and assemble them in the correct order to seal his power forever?


The initials R, KO, D, EL, and M directly correspond to core Windows architecture structures:


  1. R: Registry
  2. KO: Kernel Objects (Handles)
  3. D: Disk (MFT / Alternate Data Streams)
  4. EL: Event Logs
  5. M: Memory Map (Virtual Address Descriptors - VADs)

Challenge 2: Nice Try (Registry Hive Binary Carving & Slack Analysis)


Artifact provided: NTUSER.DAT accompanied by a cryptic hint:


"Decrypt hidden registry slack by hashing a deleted key's FILETIME with its physical-offset-sorted CRC32 payload."


1. Registry Hive Low-Level Architecture


Windows Registry hives utilize the regf container format, divided into 4096-byte hbin chunks containing individual cells. Crucially:


  • Allocated (active) cells have a negative 32-bit size field.
  • Unallocated (free / deleted) cells have a positive 32-bit size field.


Standard forensic suites only traverse active subkey lists (lf, lh, li, ri). Finding deleted data requires parsing the cell headers directly and locating unreferenced nk (named key) records.


2. Stage 1: Carving the Ghost Key


We write a binary parser to scan through all hbin blocks for nk records (0x6E 0x6B) where cell_size > 0:



From this carved nk cell, extracting the 8-byte Win32 FILETIME struct at offset 0x04:


  • Raw FILETIME: 80 ac bf ef b1 94 db 01


3. Stage 2: Physical Offset Ordering


The ghost key references a Value List (vl). The list contains 4 values. When read in logical order, the resulting bytes form random noise. However, the author's hint explicitly commanded: "physical-offset-sorted CRC32 payload".


Inspecting the physical locations of the 4 value cells within the hive file:


  • Logical sequence: [0x183020, 0x183080, 0x183040, 0x183060]
  • Ascending physical sequence: [0x183020, 0x183040, 0x183060, 0x183080]


Extracting their data buffers in physical file order produces an 8-character ASCII CRC32 hex digest:


  • Target CRC32: d03e17cb


4. Stage 3: Registry Slack Space Extraction


We compute the CRC32 of every active key name across the hive to match d03e17cb. A match is found:

Querying the values of this key:


  • Value Cfg: Declared DataLength is 12 bytes, but its allocated physical cell capacity is 124 bytes.
  • This discrepancy exposes 112 bytes of Registry Slack Space.

Challenge 3: 10X54 (ESP32-S3 Firmware Decompilation & LCG Stream Reversing)


Artifact provided: ducktricks.bin (ESP32-S3 raw firmware dump).


1. Firmware Ingestion & Xtensa Memory Mapping


Running strings confirms the binary target:



Raw ESP-IDF firmware images start with magic byte 0xE9 and consist of non-contiguous flash partitions. Direct import into disassemblers causes improper section relocation. Using esptool.py to reconstruct the ELF container restores proper address mapping (0x40374000 for IRAM, 0x3C000000 for DROM). Importing the resulting ELF into Ghidra with the Xtensa module enables clean function decompilation.


2. Dissecting the Trap Minefield


Examining app_main and the main state machine function reveals intentional obfuscation:


  • Multiple decoy arrays: FAKE_FLAG_0, FAKE_FLAG_1, FAKE_FLAG_2
  • Five 38-byte dummy buffers: DECOY_A through DECOY_E
  • An array LCG_PARAMS[8] loaded with decoy constants like 0xCAFEBABE and 0xDEADC0DE.


Tracing data flow into the genuine flag output routine reveals that only three specific buffers are actually consumed:


  • ENC_A (12 bytes)
  • ENC_B (13 bytes)
  • ENC_C (13 bytes)


These are concatenated sequentially via memcpy into a 38-byte array (ENC_TOTAL), while the decoys are completely ignored.


3. Reversing the PRNG Key Derivation


The key generation function implements a 32-bit Linear Congruential Generator (LCG):


Sn+1 = (Sn × MUL + ADD) (mod 232)


Tracking caller arguments passed into the generator:


  • Seed (S0): Derived from two 16-bit static registers: s_lfsr_hi = 0xFDD0 and s_lfsr_lo = 0x9456 → S_0 = 0xFDD09456.
  • LCG Constants: The code reads only the first two elements of LCG_PARAMS:
  • MUL = 0x6C62272E
  • ADD = 0x07354A6B


For each iteration j ∈ [0, 15], the top 8 bits of state (S[j+1] >> 24) & 0xFF are appended to form a 16-byte key.


4. Decryption Routine


The decryption routine applies a double XOR over each byte i ∈ [0, 37]:


Plaintext[i] = ENC_TOTAL[i] ⊕ (i  &  0xFF) ⊕ Key[i (mod 16)]

Analyzing Connection #1 (AA = 0xf44cca4d):


  • The client reads a nonce at 0x000E, sends an unauthenticated token to 0x0010, and reads 0x0012.
  • Across all attempts, 0x0012 consistently returns the exact same 16-byte error sentinel: e001acce55de4d00e001acce55de4d00.


Analyzing Connection #2 (AA = 0x1339a15a):


  • Nonce read (0x000E): 718d548bf9f25084be182d52c44b1bc4
  • Auth token write (0x0010): 98d27ce80f2d3628def3038e2f7b3b65
  • Response at 0x0012: 186 bytes of binary ciphertext. This is the authentic authenticated session.


4. Known-Plaintext Attack & Two-Layer Decryption


The authentication token is computed via 3-way XOR:


Token[i] = AUTH_MAGIC[i] ⊕ Nonce[i] ⊕ Key[i]


Since XOR is self-inverting, the static internal key is recovered immediately:


Key[i] = Token[i] ⊕ Nonce[i] ⊕ AUTH_MAGIC[i]


Key = ab1e7a26ba862ae927aa628dbe7163ea


The 186-byte vault payload is wrapped in two layers:


  1. Outer Layer: XOR stream keyed by SHA256(MAC ∥ Nonce)
  2. Inner Layer: XOR stream keyed by the recovered Key



Stripping both layers reveals a prompt injection honeypot:



The trailer string 1Dl0+WoRtWt... is encoded in ROT32-Base64 (shifting indices across the 64-character alphabet by 32). Decoding the rotated Base64 yields the legitimate flag:

Challenge 5: XTS-AES (ESP32-S3 Hardware Flash Encryption Bypass)


Artifacts provided:


  • efuse_sum.json (Register state dump)
  • flash_dump.bin (4 MB encrypted SPI flash memory)
  • leaked_debug_firmware.bin (Stripped ELF debug binary)


1. Cryptographic Baseline & Hardware Intel


Inspecting efuse_sum.json:


  1. SPI_BOOT_CRYPT_CNT is set → Hardware AES-XTS flash encryption is permanently enforced by the silicon controller.
  2. Device MAC address: d0:cf:13:2f:36:c8
  3. Custom user storage register:



Because hardware read protection prevents reading BLOCK_KEY0 directly, the root AES-XTS key must have been provisioned by firmware during manufacturing.


2. Reverse Engineering the Key Derivation Function (KDF)


Disassembling leaked_debug_firmware.bin in Ghidra reveals the provisioning algorithm:



  1. HMAC-SHA256: The first 24 bytes of BLOCK_USR_DATA are hashed using a 16-byte key: MASTER_CONST.
  2. PBKDF2: The intermediate key (IKM) serves as the password, salted with the device MAC address over 4,096 iterations to produce the 32-byte AES-XTS flash key.


The primary obstacle: MASTER_CONST is compiled into the firmware's .rodata section alongside multiple decoys, and stripping symbol tables removes direct cross-references.


3. Oracle Strategy: Partition Table Validation


Standard ESP32 flash layouts place the Partition Table at offset 0xA000. When decrypted with the authentic AES-XTS key, this sector must yield standard ESP partition signatures:


  • Magic bytes: 0xAA 0x50
  • ASCII partition labels such as nvs, otadata, or flagdata.


Rather than manually tracing disassembly paths, we implement a parallel candidate evaluation pipeline:


  1. Extract all candidate 16-byte chunks from the firmware image.
  2. In parallel worker pools, derive candidate XTS keys via HMAC-SHA256 + PBKDF2.
  3. Attempt AES-XTS sector decryption on offset 0xA000.
  4. Check whether the plaintext contains the partition descriptor flagdata.

Technical Summary & Core Takeaways


  1. Forensic Redundancy in Modern Operating Systems: The Green Goblin and Nice Try challenges illustrate that modern OS environments rarely allow an attacker to wipe every footprint cleanly. Even when files are stored in alternate data streams or dropped into deleted keys, telemetry caches, registry slack bytes, and VAD handle tables preserve critical forensic state.
  2. Firmware Obfuscation Does Not Substitute Cryptographic Primitives: Embedding decoy constants or bloating code with bogus Linear Congruential Generators provides only momentary friction against static taint analysis. Tracing sinks back to sources consistently strips out dead code paths.
  3. Link-Layer RF Capture Dissection: Protocols like Bluetooth Low Energy generate massive quantities of advertising frames. Pinpointing the handshake packets (CONNECT_IND) and analyzing GATT handles by their input/output properties quickly filters hundreds of noise frames down to actionable data flows.
  4. Hardware Key Derivation Attacks: Microcontroller flash encryption relies entirely on the secrecy of the root key derivation function. Stripped binaries paired with known hardware state (eFuses, MACs) are prime targets for parallel oracle-driven brute-force attacks.
