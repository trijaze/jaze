Preface


19 reports in 24 hours 🤯.


A few weeks ago, I had a bug hunting experience that surprised me in two very different ways.


I found 19 issues in one day once I realized the same trick worked across different plugins. This was my first time finding this many bugs in a row. I honestly wasn’t expecting that, especially when it feels like AI is everywhere in bug bounty lately.


Finding 19 Cross-Site Scripting vulnerabilities across 19 different plugins within a single day might sound flashy from the outside, but anyone who has spent real time auditing WordPress code knows the truth: it wasn't genius, and there was nothing superhuman about it.


It was simply a novel experience for me—a day where a specific architectural pattern clicked, the code signatures became glaringly repetitive, and tracing source-to-sink flows turned into a consistent, methodical routine.


I am sharing these notes not as a trophy case, but as a technical post-mortem, an architectural audit guide, and an honest reflection. We will look at how modern WordPress plugins—especially those bridging PHP server-side renderers with modern React frontends, Elementor widgets, and administrative export tables—repeatedly fall victim to the exact same architectural blindspots.


Note: In accordance with responsible disclosure practices and to focus purely on the defensive engineering lessons, no exploit payloads or specific attack strings are disclosed in this document. We focus strictly on the entry points, the data flows, the sink mechanisms, and the root-cause code patterns.


1. The Anatomy of Modern WordPress Architectures


A few years ago, WordPress XSS was simple: someone called echo $_GET['msg'] without esc_html().


Today, the ecosystem looks very different. The WordPress editor has evolved into the Block Editor (Gutenberg), third-party page builders like Elementor dominate theme development, and administrative dashboards are increasingly built with decoupled JavaScript frontends (React, Vue, jQuery micro-frameworks).


This architectural evolution has shifted where vulnerabilities live:


  1. The Server-to-Client Data Bridge (data-attributes): Server-side renderers (render.php) serialize block attributes as JSON and attach them to wrapper elements. PHP considers this "safe" because it calls wp_json_encode() and esc_attr().
  2. The Client-Side Hydration Sink: Client-side React scripts boot up on DOMContentLoaded, read the DOM attribute via JSON.parse(element.dataset.attributes), and mount components.
  3. The Blind Faith in Stored Block Attributes: Developers assume that because Gutenberg block attributes are saved inside post content comments (<!-- wp:block {...} -->), they are inherently clean. In reality, any authenticated user with draft editing privileges (Contributor+) can send arbitrary JSON objects in block delimiters.


Once you understand this three-step pipeline, you realize that hundreds of plugins share the exact same structural flaw.

Category A: The React `dangerouslySetInnerHTML` Hydration Flaw


This was the single most common pattern discovered across Gutenberg block collections.


The Architecture Flow:


  1. Source: A block attribute defined in block.json (e.g., title, desc, prefixText, icon.svg).
  2. Storage: The Contributor creates a post or draft containing raw block attributes inside the Gutenberg post content.
  3. Server-Side Render (build/render.php):



Why developers think it's safe: esc_attr() protects the HTML attribute itself. The page source does not execute HTML tags here.


  1. Client-Side Sink (build/view.js):



Plugins Exhibiting This Signature:


  • b-blocks (build/accordion-block/render.php): Block attributes serialized into data-attributes, hydrated by React and injected via dangerouslySetInnerHTML into accordion titles and contents.
  • advanced-post-block (build/render.php): The readMore.icon attribute parsed on the frontend in the Read More component and passed directly to raw HTML injection.
  • b-slider (build/render.php): The post slider renderer passes the full attributes object. When sourceType is set to post items, the button text property is pushed directly to dangerouslySetInnerHTML.
  • before-after-image-compare (build/render.php): The beforeLabel and afterLabel attributes are parsed from dataset.attributes and rendered via raw inner HTML.
  • button-block (build/render.php): Unsets the securityPassword attribute, but leaves the nested icon.svg object completely intact, which React mounts via dangerouslySetInnerHTML.
  • text-typing (build/render.php): Attributes prefixText and suffixText are parsed from the DOM dataset and injected directly into the React DOM tree without escaping.
  • panorama (build/blocks/product-spot/render.php): Hotspot marker icons are parsed on the client side and passed to dangerouslySetInnerHTML: { __html: hotspot.icon }.
  • stepped-content: Step navigation headings and step descriptions follow the same block attribute hydration cycle into unescaped DOM nodes.


Category B: Missing Protocol Allowlist on Client-Side Links (`href` & `iframe`)


In this pattern, developers assumed that because an attribute was rendered as an HTML attribute rather than HTML markup, standard attribute escaping (esc_attr or React JSX string binding) was sufficient.


The Architecture Flow:


  1. Source: A URL attribute (e.g., gallery[].link, btnLink, item.content).
  2. Transformation: The string is bound to the href attribute of an anchor tag <a> or the src attribute of an <iframe>.
  3. The Blindspot: React JSX automatically escapes characters like < and >, preventing tag breakouts. However, React does NOT inspect URL protocol schemes. If a string begins with a non-web scheme, React writes href="..." verbatim.
  4. The Sink: When a user clicks the button or views the iframe, the browser invokes script execution.


Plugins Exhibiting This Signature:


  • 3d-image-gallery (build/render.php): The gallery[].link attribute is passed through wp_json_encode(). On the frontend, the carousel library renders each slide wrapped in an <a> tag whose href is assigned directly from the JSON link property without validating against http:// or https://.
  • embed-lottie-player (build/render.php): The block's link attribute is passed to React's createElement("a", { href: link }) without protocol verification.
  • content-slider-block (build/render.php): The slider button link (slides[].btnLink) is parsed from data-attributes and passed directly into href: btnLink. The developer attempted to sanitize slide text, but forgot protocol validation on button destinations.
  • icon-list-block (build/render.php): Server-side sanitization runs esc_url_raw() on lists[].link, but client-side rendering uses a custom regex that preserves links on nested tags without enforcing protocol allowlists.
  • lightbox-block (build/render.php): In build/view.js, when rendering external media, the component mounts an <iframe> whose src attribute is populated directly with unvalidated item.content.


Category C: Unsanitized Options Bags in Media Players & Page Builders


This category involves plugins integrating complex third-party JavaScript libraries (such as Plyr, ArtPlayer, or custom video wrappers) or Page Builder extensions.


The Architecture Flow:


  1. Source: Plugin settings, Elementor widget options, or block settings dictionaries.
  2. The Flaw: Developers often sanitize the primary fields (e.g., video URL, poster image), but leave the generic "options" or "player config" bag uninspected.
  3. The Sink: The options dictionary is passed to the underlying player library's initialization function, which generates internal DOM elements (tooltips, controls, custom overlays).


Plugins Exhibiting This Signature:


  • html5-video-player (inc/functions.php & build/blocks/render.php): The sanitization routine h5vp_process_block_attributes() explicitly cleans source, poster, and styles, but completely ignores $attributes['options']. This configuration object is embedded in data-attributes and ingested by the Plyr player instance on the frontend.
  • media-player-addons-for-elementor (widgets/): An Elementor widget where poster metadata and video album attributes are stored in _elementor_data. When ArtPlayer initializes the player layout, it pulls the unescaped album poster configuration directly into its DOM rendering pipeline.
  • advance-custom-html (build/block/render.php): The plugin renders custom HTML blocks via PHP. In build/block/render.php, the attribute $attributes['HTML'] is output with an explicit // phpcs:ignore WordPress.Security.EscapeOutput.OutputNotEscaped comment, trusting that the user who saved the block has full unfiltered HTML rights, even when authored by a Contributor.
  • parallax-section (build/render.php): The server-side renderer applies wp_kses() to block content, but its custom $allowed_html schema explicitly permits iframe elements combined with the srcdoc attribute, allowing full nested HTML contexts to be saved and rendered.


Category D: Administrative UI & REST Collection Reflected Ingestion


Not all findings lived on the public frontend. Several lived inside the WordPress administrative interface, where administrative actions processed data generated by lower-privileged users.


The Architecture Flow:


  1. Source: Stored database records (post titles created by Contributors) or REST API collection endpoints.
  2. The Bridge: Admin JavaScript making AJAX requests to fetch records for bulk actions, export dialogs, or map marker editors.
  3. The Sink: Admin JavaScript taking server responses and inserting them into modal dialogs or table dropdowns using jQuery's .html().


Plugins Exhibiting This Signature:


  • e2pdf (js/e2pdf.backend.js & Helper_E2pdf_Field::render()): In the admin bulk export modal, E2Pdf renders a list of post datasets. When building the list of available items, js/e2pdf.backend.js reads post titles returned by the server and calls jQuery('<label>').html(option.value). Because Contributors can create posts with crafted titles, an Administrator opening the PDF export window has their browser execute the injected script.
  • mapsvg-lite-interactive-vector-maps (POST /wp-json/mapsvg/v1/collection/{collection_name}): The map marker collection REST API endpoint allows users with edit_posts privileges to save region and marker metadata. When these markers are rendered in administrative popovers or frontend views, the template engine processes unescaped Handlebars expressions (triple curly braces around description), pushing raw database content straight into the DOM.


3. The Methodology: How to Systematically Trace These Paths


Auditing 19 plugins in 24 hours was not about reading hundreds of thousands of lines of code top-to-bottom. It was about developing an efficient mental parser for modern WordPress block architectures.


Here is the exact three-step audit loop I followed:


Step 1: Pinpoint the Hydration Bridge


Whenever you inspect a plugin with Gutenberg blocks, skip the admin settings entirely. Open the build/ folder and inspect render.php. Look for one single pattern:



If the server serializes raw, unfiltered $attributes into the DOM, you have found an unvalidated bridge. The server has essentially outsourced its security to the client.


Step 2: Grep the Client-Side Sinks


Open the compiled frontend JavaScript (view.js or index.js) and search for dangerous DOM operations:


  • dangerouslySetInnerHTML
  • innerHTML
  • jQuery.html()
  • Direct property assignments to .src or .href
  • URL assignments to window.location


Trace backwards from the sink to the parsed dataset.attributes object. If the variable originates from an attribute that a Contributor can set in the editor, you have a confirmed vulnerability.


Step 3: Verify the WordPress Core Boundary


Always verify WordPress core's role in the equation:


  • Does WordPress KSES sanitize block attributes? No. KSES only inspects the post's HTML markup; it ignores JSON objects stored within block comment delimiters (<!-- wp:custom-block {...} -->).
  • Does esc_attr() protect the React DOM? No. esc_attr() only protects the browser's initial HTML parsing of the attribute tag. Once JSON.parse() reads it, the string is restored to its raw state.
  • Can a Contributor save arbitrary block attributes? Yes. Contributors have the capability to create posts and submit them for review.


When all three checks align, the flow is mathematically proven.


4. The Defensive Engineering Lessons


Why do these bugs keep happening, and how do we fix them permanently?


1. Never Trust React to Validate URLs

If a block needs to support SVG icons, don't allow users to submit raw SVG XML strings. Instead, provide a curated allowlist of icon names (e.g., 'arrow-right', 'star', 'check') and render pre-compiled, safe SVG components on the frontend.

5. The Triage Reality: What Actually Happened to the 19 Reports?


Submitting 19 reports in a single day is only half the journey. The real educational curve started when triage began.


Around 36% of my reports were rejected. Roughly half of the rejected reports were scope mistakes on my part (the stored XSS required a second action that the program didn’t cover). In other cases, vendors released patched versions roughly an hour after I recorded my PoCs, so the issues were already fixed in production by the time my reports reached the triager. In one case, the reporting platform even sanitized my payload, so it didn’t show up in the report exactly as I’d written it.


Triage OutcomeCountRatioKey Observations & Root Causes
Validated8~42%Cleanly confirmed and rewarded by program triagers


Duplicates4~21%Valid issues that other researchers had submitted earlier


Rejected (Scope / Timing / Platform)7~36%Out-of-scope secondary action, 1-hour vendor ninja patches, platform markdown payload sanitization


I’d had reports marked as duplicates before, and I’d also seen issues patched around the time I reported them. But seeing so many happen at once really surprised me and changed how I look at bug bounty.


In just 24 hours, I went from asking how? to asking why? ;-;


This dynamic may be familiar to other hunters, but it was new to me. I still enjoyed the research, learned a few lessons, and came away with 8 validated reports and 4 duplicates.


6. Personal Reflections


Stepping back from the 24-hour sprint, the experience was deeply grounding.


It taught me that bug bounty hunting isn't about guessing clever payloads or hoping for a stroke of luck. It is about understanding data flow models and recognizing the systemic blindspots created when two different paradigms—classic PHP templating and modern client-side JavaScript hydration—meet in the middle.


There will always be new frameworks, new block libraries, and new build tools. But as long as developers pass data across boundaries without defining explicit sanitization contracts, the exact same source-to-sink flows will continue to exist.


Audit the boundaries. Trace the data. Verify the framework. Everything else is just details.
