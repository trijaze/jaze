Preface


During a recent research sprint through the WordPress plugin repository, I identified 19 Cross-Site Scripting vulnerabilities across 19 different plugins within a 24-hour window.


The high volume was not the result of novel exploit payloads, but rather a recurring architectural pattern: modern WordPress plugins serializing Gutenberg block attributes into DOM data attributes, which client-side React components then ingest unsafely.


Once the data flow between PHP server-side renderers, DOM dataset bridges, and React hydration sinks became clear, finding these issues became a matter of systematic source-to-sink tracing.


These notes document the root causes, the sink categories, the audit methodology, and defensive engineering recommendations for securing modern WordPress block architectures.


Note: In accordance with responsible disclosure practices and to focus on defensive engineering, no exploit payloads or attack strings are disclosed in this document. We focus strictly on the entry points, data flows, sink mechanisms, and root-cause code patterns.


1. Modern WordPress Block Architecture


Historically, WordPress XSS often stemmed from straightforward PHP output flaws such as unescaped echo $_GET['param'].


Modern WordPress plugins frequently bridge PHP server-side renderers with client-side JavaScript frameworks (React, Vue, or frontend widget libraries). This architecture introduces a specific data flow:


  1. The Server-to-Client Data Bridge (data-attributes): Server-side renderers (render.php) serialize block attributes as JSON and attach them to wrapper elements. Developers often treat this as safe because wp_json_encode() and esc_attr() are applied.
  2. The Client-Side Hydration Sink: Client-side React scripts initialize on DOMContentLoaded, read attributes via JSON.parse(element.dataset.attributes), and mount components.
  3. Trust in Stored Block Attributes: Block attributes stored inside post content comments (<!-- wp:block {...} -->) are not sanitized by WordPress core KSES filters. Any user with post-editing capabilities (Contributor+) can submit arbitrary JSON values within these block delimiters.

Category A: React `dangerouslySetInnerHTML` Hydration


This was the most frequent pattern found in Gutenberg block libraries.


Data Flow:


  1. Source: A block attribute defined in block.json (such as title, desc, prefixText, or icon.svg).
  2. Storage: The Contributor creates a post or draft containing raw block attributes inside Gutenberg post comments.
  3. Server-Side Render (build/render.php):



esc_attr() protects the HTML attribute itself, but once parsed on the client side, the underlying JSON strings remain unescaped.


  1. Client-Side Sink (build/view.js):



Examples of Plugins with this Signature:


  • b-blocks (build/accordion-block/render.php): Block attributes serialized into data-attributes, hydrated by React and injected via dangerouslySetInnerHTML into accordion titles and contents.
  • advanced-post-block (build/render.php): The readMore.icon attribute parsed in the Read More component and injected into raw HTML.
  • b-slider (build/render.php): When sourceType is set to post items, the button text property is passed directly to dangerouslySetInnerHTML.
  • before-after-image-compare (build/render.php): The beforeLabel and afterLabel attributes parsed from dataset.attributes and rendered via unescaped inner HTML.
  • button-block (build/render.php): Clears the securityPassword attribute, but leaves the nested icon.svg object intact, which React mounts via dangerouslySetInnerHTML.
  • text-typing (build/render.php): Attributes prefixText and suffixText parsed from the DOM dataset and injected into the React tree without escaping.
  • panorama (build/blocks/product-spot/render.php): Hotspot marker icons parsed on the client side and passed to dangerouslySetInnerHTML: { __html: hotspot.icon }.
  • stepped-content: Step headings and descriptions follow the same block attribute hydration path into unescaped DOM nodes.


Category B: Missing Protocol Allowlist on Client-Side Links


In this pattern, attributes are bound to HTML attributes rather than markup. While React JSX automatically escapes characters like < and >, preventing tag breakouts, it does not inspect URL protocol schemes.


Data Flow:


  1. Source: A URL attribute (gallery[].link, btnLink, item.content).
  2. Binding: The string is bound to the href attribute of an <a> tag or src of an <iframe>.
  3. The Gap: If the string starts with javascript:, React writes the attribute verbatim.
  4. Execution: User interaction (clicking the link or loading the frame) executes the script.


Examples of Plugins with this Signature:


  • 3d-image-gallery (build/render.php): The gallery[].link attribute passed through wp_json_encode(). On the frontend, each slide is wrapped in an <a> tag whose href is assigned directly without verifying http:// or https://.
  • embed-lottie-player (build/render.php): The block's link attribute is passed to React's createElement("a", { href: link }) without protocol validation.
  • content-slider-block (build/render.php): The slider button link (slides[].btnLink) parsed from data-attributes and passed directly into href: btnLink.
  • icon-list-block (build/render.php): Server-side sanitization runs esc_url_raw(), but client-side rendering uses custom regex transformations that bypass the allowlist.
  • lightbox-block (build/render.php): In build/view.js, an <iframe> has its src populated with unvalidated item.content.


Category C: Unsanitized Options Bags in Media Players


This pattern occurs when plugins integrate third-party JavaScript libraries (such as Plyr or ArtPlayer).


Data Flow:


  1. Source: Plugin settings or block settings dictionaries.
  2. The Gap: Primary fields (video URL, poster) are sanitized, but a generic "options" or "config" bag is left uninspected.
  3. The Sink: The options dictionary is passed to the player library's initialization function, which renders internal DOM elements (tooltips, controls, overlays).


Examples of Plugins with this Signature:


  • html5-video-player (inc/functions.php & build/blocks/render.php): h5vp_process_block_attributes() sanitizes source, poster, and styles, but ignores $attributes['options'], which is ingested by Plyr on the frontend.
  • media-player-addons-for-elementor (widgets/): Elementor widget where metadata is stored in _elementor_data. When ArtPlayer initializes, it processes the unescaped poster configuration directly into its DOM pipeline.
  • advance-custom-html (build/block/render.php): The attribute $attributes['HTML'] is output with a PHPCS ignore comment, allowing Contributor-authored markup to render unfiltered.
  • parallax-section (build/render.php): Uses a custom $allowed_html schema with wp_kses() that permits iframe elements combined with srcdoc.


Category D: Administrative UI and REST Reflected Ingestion


Several findings affected the administrative interface, where actions performed by administrators processed data created by lower-privileged users.


Data Flow:


  1. Source: Stored database records (such as post titles created by Contributors) or REST API endpoints.
  2. The Bridge: Admin JavaScript making AJAX requests to fetch records for bulk actions or export dialogs.
  3. The Sink: Admin JavaScript inserting server responses into dialogs or table dropdowns using jQuery's .html().


Examples of Plugins with this Signature:


  • e2pdf (js/e2pdf.backend.js & Helper_E2pdf_Field::render()): In the bulk export modal, e2pdf.backend.js reads post titles from server responses and executes jQuery('<label>').html(option.value). When an administrator opens the PDF export dialog, post titles authored by Contributors are rendered as HTML.
  • mapsvg-lite-interactive-vector-maps (POST /wp-json/mapsvg/v1/collection/{collection_name}): Map marker metadata saved by users with edit_posts permissions is rendered in popovers using unescaped Handlebars expressions (triple curlies).


3. Audit Methodology


Systematically auditing modern WordPress plugins for these issues involves a three-step review loop:


Step 1: Locate the Hydration Bridge


Inspect render.php in the plugin's build directory and look for attribute serialization:



When raw $attributes are passed to wp_json_encode(), the server relies entirely on the client to handle safety.


Step 2: Trace Client-Side Sinks


Search compiled frontend scripts (view.js or index.js) for DOM injection sinks:


  • dangerouslySetInnerHTML
  • innerHTML
  • jQuery.html()
  • Direct assignments to .src, .href, or window.location


Trace the variable backwards to verify whether it originates from dataset.attributes.


Step 3: Verify Role Boundaries


  • WordPress KSES: KSES sanitizes HTML markup, but ignores JSON objects inside block comment delimiters (<!-- wp:custom-block {...} -->).
  • esc_attr() scope: esc_attr() protects attribute parsing in the initial HTML document. Once JSON.parse() reads it, the string is restored to its original value.
  • Authoring privileges: Contributors hold the capability to create posts and submit them for review.


When these conditions align, the path from untrusted input to execution sink is confirmed.

5. Triage Breakdown


Submitting 19 reports provided useful data on triage outcomes:

Roughly half of the rejections stemmed from scope definitions regarding secondary user interaction. In other cases, vendors released patched versions shortly after report recording.


6. Takeaway


The main lesson from this audit sprint is that framework boundaries create security gaps. As long as server-side PHP templates hand data to client-side JavaScript without enforcing an explicit sanitization contract, identical source-to-sink flows will continue to appear.
